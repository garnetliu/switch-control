## 流程

任务交给 dispatcher（`.claude/agents/dispatcher.md`），它负责派活、转交和判断，自己不写代码、不验收。每个任务过三个角色：

| 角色 | agent | 做什么 | 能改什么 |
|---|---|---|---|
| 写测试 | `test-writer` | 按任务文件「写测试」一节写测试，这时实现还没做，测试跑不过是正常的；验收不通过时，把能写成测试的问题写成复现用例 | 只能改 `tests/` |
| 开发 | `implementer` | 把任务要的功能完整做出来，改到测试全部通过，自己跑一遍验证 | 不能改 `tests/` |
| 测试 | `reviewer` | 站在用户的角度把任务完整测一遍，包括连真机跑；任务文件「测试」一节是最低要求，之外还要自己找问题。只给判决（JSON） | 什么都不改 |

1. test-writer 写测试。
2. implementer 开发。觉得测试写错了，写进报告，dispatcher 转给 test-writer 判断。
3. reviewer 验收。不通过时：测试本身写错的，交给 test-writer 改；代码的问题能写成测试的，先由 test-writer 写成现在失败、修好后通过的用例，这些用例留在项目里，以后再出同样的问题会被拦住；然后代码的问题转给 implementer 逐条改。都改完交给同一个 reviewer 照上一轮的复现方式重验。
4. reviewer 判通过，或者同一条来回 3 轮没解决、总共 5 轮，这个任务停止。

- 几个任务可以同时做：每个任务一个带名字的 implementer，在同一个目录里改，改同一个文件前用 SendMessage 互相商量。test-writer、reviewer 不和 implementer 直接对话，都经 dispatcher 转。
- test-writer 同一时间只跑一个，它们会改到 `tests/conftest.py` 这类共用文件。
- Switch 只有一台，会连 Switch 的命令同一时间只给一个 agent 跑，由 dispatcher 分配，并写明跑到哪里停。
- 每个角色只拿到当前这一个任务的文件，看不到其他任务和这份总览。
- 写法好不好，对照 `.claude/skills/` 下的规范：`python-best-practices`、`design-patterns`、`architecture`、`testing-tdd`、`type-safety`、`error-handling`。
- 用到某个库的接口之前，先在项目已安装的版本里确认（看 `.venv` 里的源码，或者实际调用一次），不凭记忆写。OpenCV、rapidocr、pyusb、pyserial、pytest、hatchling 这些库没有现成的规范可以对照。
- 后面的环节发现任务文件写错或漏了，停下来问人，回去改任务文件，不让角色自己绕过去。
- 谁都不提交。任务通过之后由人来提交。

## 类型检查怎么算通过

- 类型检查用 pyright 的标准模式（`standard`），不用严格模式。
- 每个任务做完，`make typecheck` 都要 0 报错，范围是 `src/control_switch/` 和 `tests/`。
- 搬进来的旧代码原来就有的类型报错，由搬它的那个任务清掉。可以用的办法只有这几种：补类型标注；给变量赋初值；加 `assert` 判空；用 `typing.cast`。
- 不用 `# type: ignore` 和 `# pyright: ignore` 把报错压掉。第三方库没有类型信息造成的报错确实绕不开时可以用，要在同一行写明原因。
- 这些改动都不能改变正常运行时的结果。
- 核对搬过去的文件内容有没有变时，允许的改动是：import；上面这几种为清类型报错做的改动；这个任务「实现」里明确写了的其他改动。
