# 任务 10：交叉组合验证

## 目标

确认取图、按键、内存三项可以随意组合：每一种组合都能创建出设备、通过启动检查；接错的情况能被启动检查拦住，报错能让人看出是哪里接错了。

为了能在没破解的机器上验证（两个脚本现在都需要内存，在那台机器上跑不了），加一个只做启动检查、不跑脚本的命令。

## 开始前的状态

- 取图有两种：`botbase`、`capture`（采集卡）。按键有两种：`botbase`、`serial`（单片机）。内存有两种：`botbase`、`none`。都已经实现。
  - 采集卡：`device/capture_card.py` 的 `<类名>`，`device/factory.py` 用 `<配置项>` 创建它。打不开时抛 `<异常>`，报错是「<报错文字>」。测试里把 `<模块.名字>` 换成假的，就不会去打开真的采集卡；`tests/conftest.py` 里的假设备叫 `<fixture 名>`。
  - 单片机：`device/serial_pad.py` 的 `SerialPad`，`device/factory.py` 在 `CONTROLLER=serial` 时用 `open_serial_pad(settings)` 创建它（读 `SERIAL_PORT`、`SERIAL_BAUD`）。串口打不开时抛 `DeviceCheckError`，报错是「按键：串口 <路径> 打不开：<原来的报错>」；没有回应时抛 `DeviceCheckError`，报错是「按键：单片机没有回应（<握手或停脚本>，收到 <十六进制或空>），……」。测试里把 `control_switch.device.factory.open_serial_pad` 换成返回假按键设备的函数，就不会去打开真的串口；`tests/conftest.py` 里的假按键设备是 fixture `controller`（`FakeController`）。
  - botbase：`device/factory.py` 用 `connect_botbase(settings)` 建连接。测试里把 `control_switch.device.factory.connect_botbase` 换成返回假设备的函数，记下被调了几次。
  - 采集卡、单片机这两条里尖括号的内容，要等采集卡（任务 08）、单片机（任务 09）的约定定下来之后照抄补上，补完之前不能开始这个任务。
- `create_devices(settings)` 按 `.env` 的 `SCREEN`、`CONTROLLER`、`MEMORY` 创建设备，选了 `botbase` 的几项共用一个连接。
- `device/factory.py` 用 `from .botbase import connect_botbase` 引用连接函数；`__main__.py` 用 `from control_switch.device import check_devices, create_devices` 引用。测试里替换的是使用它们的模块上的名字，改这两个文件时不要换引用写法。
- `check_devices(devices, requires, title_ids)` 检查单个设备；`check_controller_reaches_screen(sw)` 按 HOME 确认按键送到了画面上的这台机器。
- 命令行有 `run`、`restart` 两个命令。
- 手上有两台机器：一台破解的（能用 botbase），一台没破解的（只能用采集卡和单片机）。

## 约定

### 所有组合

一共 2 × 2 × 2 = 8 种：

| 编号 | SCREEN | CONTROLLER | MEMORY | 要不要连 botbase |
|---|---|---|---|---|
| 1 | botbase | botbase | botbase | 要 |
| 2 | botbase | botbase | none | 要 |
| 3 | botbase | serial | botbase | 要 |
| 4 | botbase | serial | none | 要 |
| 5 | capture | botbase | botbase | 要 |
| 6 | capture | botbase | none | 要 |
| 7 | capture | serial | botbase | 要 |
| 8 | capture | serial | none | 不要 |

- 要连 botbase 的组合，不管有几项用它，只连接一次。
- 第 8 种不去连 botbase，没有 botbase 的机器上也能创建成功。

### `check` 命令

- `control-switch check`：不带脚本名。按 `.env` 创建设备，做启动检查，然后退出，不跑任何脚本。
- 跑 `check` 前，Switch 上要开着一个游戏，画面停在游戏里或者 HOME 菜单上都可以。没开游戏时，HOME 菜单上按 HOME 画面不会变，HOME 那项一定失败。
- 第一步先调 `init_console()`，在读配置和 `create_devices` 之前，和 `run`、`restart` 一样。`init_console()` 要在第一条日志之前调：根 logger 还没有输出时记日志（比如 `check_devices` 记全黑的警告），Python 会自动加一个默认格式的终端输出，之后 `log.py` 就不再加自己的，整次运行的终端日志都没有时间，也不挡第三方库的日志。`__main__.py` 已经用 `from control_switch.log import init_console, init_log` 引用这两个函数，不要换引用写法。
- 检查的内容：
  1. `check_devices(devices, 空的 requires, None)`：只检查取图，不要求内存，不检查是哪个游戏。
  2. 配置了内存时，读一次 `title_id()`，用 `print` 把读到的值输出到标准输出。读到的是空的不算错，用 `print` 输出「没有游戏在运行」，接着做下一项。
  3. 按 HOME 的那项检查：用 `Session(BaseConfig(), settings, devices)` 建 `sw`，不用哪个脚本的 `SESSION`；调 `init_log(sw, "check")`，日志写到 `logs/check/` 下；然后调 `check_controller_reaches_screen(sw)`。
- `__main__.py` 里用 `from control_switch.flow.check import check_controller_reaches_screen` 引入，按这个名字调用。测试替换的是 `control_switch.__main__.check_controller_reaches_screen`。
- 全部通过时用 `print` 把用的是哪种取图、哪种按键、哪种内存输出到标准输出，然后 `main` 正常返回，不抛 `SystemExit`（命令行的退出码是 0），和 `run` 成功时一样；不通过时用 `sys.exit(报错文字)` 退出：Python 会把报错文字打到标准错误，退出码是 1。
- 下面几种都算不通过，都按上一条退出，不打印 traceback：`create_devices`、`check_devices`、`check_controller_reaches_screen` 抛 `DeviceCheckError`；`load_settings` 抛 `ValueError`（配置的值不认识、`SWITCH_PORT` 不是整数）；`create_devices` 抛 `ValueError`（WiFi 连接缺 ip 或端口；没装 libusb 时 pyusb 抛的 `NoBackendError` 也是 `ValueError`）或 `NotImplementedError`。这和 `run` 处理这几种异常的方式一样。
- `Makefile` 加 `check`：`uv run control-switch check`。

### 接错的情况

下面每种情况启动检查都要报错，并且报错能区分开：

| 情况 | 报错要说明 |
|---|---|
| 采集卡没插，或者序号不对 | 取图：设备打不开 |
| 采集卡插着但没有画面（Switch 没在底座上，或者没给摄像头权限） | 取图：全黑，记警告；接着 HOME 那项会失败 |
| 单片机的串口没插，或者串口号不对 | 按键：串口打不开 |
| 串口能打开，但单片机没有回应 | 按键：没有回应 |
| 采集卡接的是一台，按键送到的是另一台 | 按了 HOME 画面没有变化 |
| 单片机没被 Switch 认成手柄 | 按了 HOME 画面没有变化 |
| 脚本需要内存，`MEMORY=none` | 这个脚本要读内存 |
| botbase 连不上（没破解的机器，或者 ip 不对） | 写明是 botbase 连接失败，以及是 WiFi 还是 USB |

## 写测试

只能改 `tests/`。用假设备，采集卡、单片机的假设备和测试要替换的名字见「开始前的状态」。假设备都通过 `tests/conftest.py` 里的 fixture 拿，测试文件里不能写 `from conftest import ...`。

1. `tests/device/test_factory.py`，把 `control_switch.device.factory.connect_botbase` 换成返回假设备的函数并记下被调了几次，用参数化把 8 种组合各测一遍：
   - 每一项拿到的是对应种类的设备。
   - 要连 botbase 的 7 种，连接函数只被调了一次，用到 botbase 的几项是同一个对象。
   - 第 8 种，连接函数没有被调。
   - `MEMORY=none` 的 4 种，`memory` 是 `None`。
2. `tests/device/test_check.py`，用参数化把 8 种组合各过一遍 `check_devices`：
   - `requires` 是三样都要时：`MEMORY=none` 的 4 种报错，其余 4 种通过。
   - `requires` 只有取图和按键时：8 种都通过。
3. `tests/test_session.py`，8 种组合各建一个 `Session`：
   - `click` 送到了这个组合的按键设备，`pixel_peek` 来自这个组合的取图设备。
   - `close()` 之后每个不同的设备各关了一次，没有关两次的。
4. `tests/test_main.py`，`check` 命令。把 `control_switch.__main__.create_devices` 换成返回假设备的函数。项目里没有 HOME 菜单的截图，把 `control_switch.__main__.check_controller_reaches_screen` 换成假的：「按 HOME 画面不变」那条让它抛 `DeviceCheckError`，其余几条什么都不做：
   - 假设备都正常：`main(["check"])` 正常返回，不抛 `SystemExit`；`title_id()` 被读了一次；`capsys.readouterr().out` 里有三项各自的种类，还有假 `Memory` 的 `title_id()` 返回的值。
   - 取图返回不是图片的字节：以非 0 退出。
   - 按 HOME 画面不变：以非 0 退出。
   - `MEMORY=none`：不读 `title_id`，照样通过。
   - 假 `Memory` 的 `title_id()` 返回空字符串：`main(["check"])` 照样正常返回，标准输出里有「没有游戏在运行」，`check_controller_reaches_screen` 照样被调了一次。
   - 把 `control_switch.__main__.init_console` 和 `control_switch.__main__.create_devices` 都换成记下调用顺序的函数：`init_console` 在 `create_devices` 之前被调了。
   - 不认识的脚本名之类的多余参数：报用法错误。
   - 用 `monkeypatch.setenv` 把 `SCREEN` 设成 `hdmi`：`main(["check"])` 抛 `SystemExit`（不是 `ValueError`），退出码不是 0，`create_devices` 没有被调。
   - `create_devices` 换成抛 `ValueError` 的函数、换成抛 `NotImplementedError` 的函数，各一次：`main(["check"])` 都抛 `SystemExit`，退出码不是 0。
5. 「接错的情况」表里能用假设备做出来的每一行各写一条测试，断言报错里有表里写的那句说明。通过 `main(["check"])` 测的，报错文字从 `pytest.raises(SystemExit)` 拿到的 `code` 里读，不从标准错误或日志里读。
   - 「botbase 连不上」这一行：把 `control_switch.device.factory.connect_botbase` 换成抛 `ConnectionError` 的函数，`usb`、`wifi` 各测一次，分别断言报错里有 `botbase`、`连接失败`，以及 `USB` 或 `WiFi`，不断言整段连在一起的文字。
   - 「采集卡插着但没有画面」这一行不是报错：取图返回全黑的 16:9 图，`control_switch.__main__.check_controller_reaches_screen` 换成抛 `DeviceCheckError` 的函数。断言有一条级别是 `WARNING` 的日志（用 `caplog`），`check_controller_reaches_screen` 被调了（全黑没有让检查提前停下），`main(["check"])` 以非 0 退出。不要断言报错里有「全黑」。
   - 「采集卡接的是一台，按键送到的是另一台」「单片机没被 Switch 认成手柄」这两行，报错来自真的 `check_controller_reaches_screen`，不用换成假的那个：用假设备建 `Session(BaseConfig(), settings, devices)` 当 `sw`；用 `monkeypatch.setattr` 把 `control_switch.flow.check.home_shown` 换成不管传什么都返回 `False` 的函数（按了 HOME 画面一直不变），把 `control_switch.config.BaseConfig.check_timeout` 改成 `0.1`；直接调 `control_switch.flow.check.check_controller_reaches_screen(sw)`，断言抛 `DeviceCheckError`，报错里有「按了 HOME 画面没有变化」。这两行做法一样，写一条测试就行。

## 实现

不能改 `tests/`。

1. `__main__.py` 加 `check` 命令，按「约定」写。
2. `Makefile` 加 `check`。
3. 跑测试，8 种组合里有不通过的，修对应的地方：`device/factory.py`、`device/check.py`、`session.py`。
4. 「接错的情况」表里报错说明不够清楚的，改报错的文字。
5. `README.md` 加一段：8 种组合的表、`make check` 的用法（跑之前 Switch 上要开着一个游戏）、每种报错是什么意思。「命令」表在 `make restart` 那一行后面加一行 `make check`，作用写「只做启动检查，不跑脚本，跑之前 Switch 上要开着一个游戏」；目录说明里 `logs` 那一行补上 `make check` 的日志在 `logs/check/`。`.env.example` 里三项的说明和 README 对上。

## 测试

下面是至少要过的检查，逐条写出结果。这些之外还要按用户的用法自己找问题。自己找问题时，不运行 `make start`、`make restart`、`make check`，也不运行不写脚本名或者写了能用的脚本名的 `control-switch run`、`control-switch restart`，以及 `control-switch check`（包括 `uv run` 和 `python -m control_switch` 的写法），它们会连接 Switch，或者打开采集卡和单片机的串口；也不运行 `make find`，它会改写 `.env`。这一节里明确写出的命令除外。需要连着 Switch 才能确认的，在结果里列出来，交给人在真机上确认。

1. `make test` 全部通过。
2. `make lint` 没有新增的报错。
3. `make typecheck` 0 报错。
4. `SCREEN`、`CONTROLLER`、`MEMORY` 各写一个不认识的值，`SWITCH_CONNECTION=wifi SWITCH_IP=127.0.0.1 SWITCH_PORT=1 uv run control-switch check` 都报错退出，报错里写明可以写的值，没有打印 traceback，输出里没有 `Connection refused`。
5. `README.md` 里的组合表和「约定」里的表一致，「命令」表里有 `make check`，`logs` 那一行写了 `logs/check/`；`.env.example` 里三项可以写的值和 `settings.py` 里的一致。
6. `SWITCH_CONNECTION=wifi SWITCH_IP=127.0.0.1 SWITCH_PORT=1 uv run control-switch check 多余的参数` 报用法错误，输出里没有 `Connection refused`。命令行上设的环境变量优先于 `.env`，前面三个环境变量把 botbase 连接指到本机一个没有程序在听的端口：实现写错、真的去连了的话，会马上报 `Connection refused`，不会连上插着的 Switch。
7. `grep -rnE "device(\.| import .*)(botbase|capture_card|serial_pad)" src/control_switch --include="*.py" | grep -v "^src/control_switch/device/"` 没有结果，说明 `device` 外面没有引用 `botbase`、`capture_card`、`serial_pad` 这三个具体实现。
8. `make coverage` 的输出里，`__main__.py` 的 `check` 命令、`device/factory.py`、`device/check.py`、`session.py` 没覆盖到的行，要么补上测试，要么逐处写明为什么测不了。

## 要在真机上确认的

下面每次跑 `make check` 前，Switch 上都先开着一个游戏，写明不开游戏的那一条除外。

破解的那台，每种组合改 `.env` 后跑 `make check`，再跑 `make start` 打一局极巨大冒险：

| 组合 | SCREEN | CONTROLLER | MEMORY |
|---|---|---|---|
| 1 | botbase | botbase | botbase |
| 3 | botbase | serial | botbase |
| 5 | capture | botbase | botbase |
| 7 | capture | serial | botbase |

破解的那台，组合 1 和 7 各跑一次 `make start script=sv/outbreak`。

没破解的那台：

- 组合 8（capture、serial、none）跑 `make check`，通过。
- 组合 8，开着游戏、画面停在 HOME 菜单上跑 `make check`，通过。
- 组合 8，不开任何游戏、停在 HOME 菜单上跑 `make check`，报错说明按了 HOME 画面没有变化。
- 组合 8 跑 `make start`，报错说明这个脚本要读内存。
- 组合 7（MEMORY=botbase）跑 `make check`，报错说明 botbase 连接失败。

接错的情况，两台机器都开着：

- 采集卡接破解的那台，单片机接没破解的那台，跑 `make check`，报错说明按了 HOME 画面没有变化。
- 拔掉采集卡跑 `make check`，报错说明取图设备打不开。
- 拔掉串口模块跑 `make check`，报错说明串口打不开。
- 串口模块插着，单片机的 USB 不插 Switch，跑 `make check`，报错说明按了 HOME 画面没有变化。

采集卡加 usb-botbase 这个组合接不接得了，也在这里试一次：能接就照常验证，接不了记下启动检查报的是什么。
