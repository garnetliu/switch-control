# 重构：任务拆分的审查计划

## 为什么要审

`docs/重构/任务/` 下的任务是一个人拆的，没有别人看过。拆得有漏、有错、顺序不对，后面三个角色照着做也只会把错的东西做出来。

三次独立的结果一致，只能说明输出稳定，不能说明没有漏。所以这份计划分两部分：一部分靠多次独立运行找不一致，一部分用不依赖模型判断的清单找「大家都漏了」的东西。

## 输入

- [需求和结构.md](需求和结构.md)：已经定下来的需求和目录结构。
- 项目的代码。

审查方看不到这份计划，看不到总览。

## 第一步：三方各自独立拆一遍

目的：查漏、查顺序。

- 起 3 个 subagent，给的东西完全一样：`需求和结构.md` 加上代码库。
- 不给它们现有的任务文件。看到现成的拆法，容易顺着它走，查不出漏的。
- 每个各自输出一份「要做的事项」清单，每一项写：
  - 做什么。
  - 动哪些文件。
  - 必须在哪些事项之后做。
  - 怎么算做完。
- 互相看不到对方的结果。

然后把这 3 份清单和现有的任务文件放在一起逐条对比，一共 4 方。对比的单位是「一件具体的事」，比如「`find_switch.py` 里算根目录的那一行要改」，不是整个任务。

## 第二步：三方各自核对现有的任务文件

目的：查错。

- 再起 3 个 subagent，给的东西完全一样：`需求和结构.md`、全部任务文件、代码库。
- 每个各自对每个任务文件逐节核对：
  - 「开始前的状态」写的和代码是否一致：文件在不在、函数名和类名对不对、引用关系对不对。按任务的顺序推：前面的任务做完之后，这一节写的状态是不是真的成立。
  - 「约定」有没有歧义，两个人照着写会不会写出不一样的东西；任务之间的约定有没有互相矛盾。
  - 「写测试」里的每一条能不能写出来，需要的图片和数据有没有。
  - 「实现」做完之后，项目是不是真的还能跑；有没有漏掉要跟着改的文件。
  - 「测试」里的每条命令能不能运行，能不能真的检查到它想检查的东西。
- 每个输出一份问题清单，每个问题写明在哪个任务文件的哪一节、依据是代码里的哪里。

## 第三步：处理不一致

第一步和第二步的结果都按同一套规则处理。

**一致的**（第一步是 4 方都有，第二步是 3 方都报）：直接采用。

**不一致的**（只有一部分提到）：每一条单独拿出来，起 3 个 subagent 各自独立审，只给这一条、相关的任务文件和代码。每个回答：

1. 这一条成立不成立，依据是代码里的哪里。
2. 为什么有的提到了、有的没提到：没提到的是漏了，还是提到的判断错了，还是输入本身有歧义。

三次的结论：

| 结论 | 处理 |
|---|---|
| 3 次都说成立 | 采用，改任务文件 |
| 3 次都说不成立 | 丢掉，在审查记录里留一笔 |
| 2 比 1 | 连同三次的理由交给人决定 |
| 原因是 `需求和结构.md` 有歧义 | 先改 `需求和结构.md`，这一条涉及的部分重新走第一步 |

## 第四步：用清单找「都漏了」的

三方一致不代表没漏。这一步不靠模型判断，靠把东西一项一项列出来、每一项都要有着落。清单用命令从项目里直接提取，不手写。

| 清单 | 怎么列出来 | 每一项要对上什么 |
|---|---|---|
| 文件 | `git ls-files` 的全部文件 | 哪个任务动它，或者写明不动 |
| 引用 | 代码里所有 `import`、`from ... import` 的模块名 | 任务文件的引用对照表里有它 |
| 目标结构 | `需求和结构.md` 目录树里的每个文件 | 哪个任务把它建出来 |
| 需求 | `需求和结构.md` 里带编号的每一条 | 哪个任务实现它，哪条检查能证明做到了 |
| 对外的用法 | `Makefile` 的每个命令、`.env.example` 的每一项、命令行的每个参数 | 重构后还在不在、哪个任务会碰它 |
| 运行时读写的位置 | 代码里所有读写文件的路径（日志、截图、存档状态、数据文件、`.env`） | 移动文件后位置变不变、哪个任务确认了 |
| 文档里提到的路径和名字 | `README.md`、`docs/`、`AGENTS.md`、`docker/` 里出现的旧路径、旧模块名、旧类名 | 哪个任务会改它，或者写明不改 |
| 环境变量 | 代码里读的每个环境变量 | `settings.py` 的任务里有它 |

对不上的每一项就是一个漏，按第三步的规则处理：先当作「不一致的条目」单独审 3 次，确认成立再改任务文件。

结果存成 [覆盖表.md](覆盖表.md)，每个清单一张表。

## 第五步：换角度再找一遍

第一步的 3 个 subagent 输入完全一样，容易漏同一类东西。这一步再起 3 个，每个给一个不同的角度，输入里不带前面的结论：

| 角度 | 做什么 |
|---|---|
| 使用者 | 把现在能做的每件事列出来（照 `README.md`、`Makefile`、`.env.example`），一件一件看重构后还能不能做、怎么做 |
| 文件 | 从每个源文件出发，跟着它被谁引用、引用了谁，看它搬走之后哪些地方会断 |
| 运行 | 按任务顺序一个一个推，假装每个任务刚做完，照着启动流程走一遍，看会断在哪 |

这一步三个的输出本来就不一样，所以全部按「不一致的条目」处理，每条单独审 3 次。

## 收敛

- 第一步到第五步算一轮。一轮下来有被采用的条目，就改任务文件，再来一轮。
- 一轮下来没有任何被采用的条目，算收敛，停下。
- 最多 3 轮。3 轮还有新条目，停下，把情况交给人。
- 第二轮起只重跑受上一轮改动影响的部分：改过的任务文件、依赖它的后续任务。覆盖表每轮都全部重新生成。

## 还是会漏的怎么办

上面做完仍然可能有漏的，后面要有地方接住：

- **执行中发现**：三个角色里任何一个发现任务文件漏了或错了，停下来报告。处理是改任务文件，不是让它自己想办法绕过去。
- **追到根上**：每发现一个前面审查没查到的问题，要回答它属于哪一类、为什么第四步的清单没列到它。能加成一种新清单的就加，然后对还没做的任务重新过一遍这种清单。
- **最后验收**：全部任务做完后，拿 `需求和结构.md` 逐条验收：带编号的每条需求有没有做到，目录结构和定下的是不是一致，各层的规则有没有被违反。

## 产出

- 改好的任务文件和总览。
- [覆盖表.md](覆盖表.md)：第四步的清单和对应关系。
- [审查记录.md](审查记录.md)：每一条的来源、几方提到、单独审查的三次结论和理由、最后怎么处理。丢掉的也记。

## 规模

每一轮的 subagent 数量：

| 步骤 | 数量 |
|---|---|
| 第一步 | 3 |
| 第二步 | 3 |
| 第三步 | 不一致的条目数 × 3 |
| 第四步 | 不用 subagent，用命令 |
| 第五步 | 3 |

不一致的条目有多少，要跑了第一轮才知道。条目多的时候，相关的几条合在一起审，一个 subagent 一次审一个任务文件里的全部条目。
